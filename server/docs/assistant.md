# Kamand assistant

The signed-in workspace has an Assistant button. The server uses `GEMINI_API_KEY` and `GEMINI_MODEL` (default `gemini-3.8-flash`) from its environment. Credentials never reach the client bundle. Docker Compose reads `server/.env`; Azure's deployment script supplies the key as a Container Apps secret.

`POST /api/assistant` accepts either `{message, sessionId?, conversationId?}` or `{sessionId, decision: "confirm" | "cancel", approvalId}`. Replies have `{data: {sessionId, status, message, suggestions, actions, approval?}}`. Status is `completed`, `confirmation_required`, or `error`. Actions contain actual API status, success and results, including partial completion when a later provider call fails. An HTTP-success response can contain an assistant error; consumers must inspect `status` and `actions`.

Gemini receives a JSON response schema and named function declarations generated from the REST route catalogue. The server validates replies with Zod, preserves provider thought signatures, executes read calls, and pauses writes for an exact action preview. Confirmations are bound to the user, session and one-time approval ID. Cancelling returns cancellation results to the model. Never retry a write automatically after a transport failure; inspect the app and the action results first.

Tools cover user search and profiles; residence preferences; direct and group chats; group membership; messages, search, read receipts and reactions; existing attachments; joining campus rooms and checking permissions; mess menus; calendar events and maintenance tickets. Binary file uploads use the existing app upload controls. Authentication/password changes, arbitrary URLs, OS commands, external services and local-only visual preferences are not assistant tools. The server always forwards the caller's bearer token to its own loopback API. Existing route validation, database permissions, campus manager scopes and realtime events remain authoritative. It never uses an admin credential.

Requests, retrieved messages and relevant app data are sent to Gemini. Conversation context is stored server-side in bounded in-memory sessions for 30 minutes of inactivity, with 500 sessions maximum, 80 transcript entries and eight model rounds per request. New assistant conversation clears the client session reference; old sessions expire automatically. Sessions do not survive server restarts or cross replicas; keep the API at one replica until this state and rate limiting move to shared storage. Concurrent requests to a session are rejected. Rate limit: 12 assistant requests per user per minute. Request deadline: 90 seconds, client deadline: 100 seconds.

Run `npm test` and `npm run typecheck` in `server`, and the corresponding client checks. Run `npx tsx scripts/check-gemini.ts` in `server` for a live read-tool capability check without production records or mutations. This check uses the configured provider key and can consume API quota.

The live check runs the actual assistant handler, including its system prompt, JSON schema, provider wrapper, function responses and Zod validation. It uses an isolated synthetic identity and empty tool results; it does not read production records. Temporary provider failures (HTTP 408/500/502/503/504 or transport errors) retry generation up to two times within the existing request deadline. Tool execution never retries. Permanent key, permission, model, request-format and quota errors return distinct `errorCode` values. Server logs include HTTP status, configured model, attempt and diagnostic code, never raw provider error bodies or credentials.

Provider references: [function calling](https://ai.google.dev/gemini-api/docs/generate-content/function-calling), [structured output](https://ai.google.dev/gemini-api/docs/generate-content/structured-output). The live API was verified using REST `responseMimeType` and `responseJsonSchema`; `responseFormat` was rejected by the endpoint during verification.
